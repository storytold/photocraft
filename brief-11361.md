## The bug

An Outer Glow whose contour is above 0 at its left end — e.g. a flat contour (0,255)–(255,255), "always 100 %" — is painted over the whole rectangle the effect is computed in (layer bounds + glow reach), with square corners. Photoshop paints only where the glow reaches: a solid band *Size* px wide following the shape, with a soft outer edge. Both techniques (Precise and Softer), on PSD import and natively (`layer.layerStyle.outerGlow` with `"contour": {"points": [[0,1],[1,1]]}`).

## The reporter's diagnosis (verify against the code, then build on it)

- `glow_map` in `crates/compose/src/effects/paint.rs` maps the whole coverage buffer through the contour (`m = apply_lut(m, glow_lut(g))`), including pixels the glow does not reach (coverage 0). With `contour(0) > 0` those pixels light up too, out to the buffer's edge.
- The GPU path uses the same table (`fx::glow_lut` in `crates/gpu/src/fx/builders.rs`), so it does the same. A complete fix covers both paths, or fixes the shared table construction so both inherit it.
- The reporter attached a work-in-progress patch and explicitly offers it as a starting point, not a fix: https://github.com/user-attachments/files/34404901/glow-contour-fix.patch (curl it; it applies cleanly to main). What it does: a new `glow_paint_lut(g, inner)` sets the table's first entry — the one coverage-0 pixels consult — so unreached pixels stay dark. That removes the rectangle, but the band's outer edge still doesn't match Photoshop. Start by applying it in the worktree, understanding exactly what it changes, and treat the remaining edge mismatch as the real problem to solve. Credit the reporter in your summary.
