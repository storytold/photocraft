# Options: протокол совместного редактирования для PhotoCraft

> Артефакт Phase 0. Три варианта, различающиеся **механизмом** (кто исполняет намерение и
> что летит по проводу), а не настройками. Факты — из `study.md` (ссылки на файлы
> upstream). Кода фичи здесь нет.
>
> **Канон букв шины (ADR 0001).** A — реплей намерения на клиентах; B — сервер исполняет и
> рассылает авторитетный результат; C — CRDT. Ниже буквы строго в этом смысле.

- Проект: `photocraft`, upstream `storytold/photocraft` @ `830316b77` (0.23.1)
- Дата: 2026-11-25, автор: `photocraft/envoy` (craft-scout)
- Критерии: `.craft/protocol/AGENDA.md` §«Критерии оценки варианта»

## 1. Вариант A — журнал намерений + операционные дельты с OT (исполняют клиенты)

Единица — **нормализованная операция над моделью**, а не команда: `SetLayerProps`,
`PaintTiles{layer, part, tiles:[(coord, zstd)…]}`, `InsertLayer{id, anchor, position}`,
`SetAdjustment`, `SetTextRuns`, `Reorder{layer, anchor, position}`. Клиент исполняет свою
операцию сам, шлёт её всем; получатель **трансформирует** её против своих непринятых
операций (OT) и применяет напрямую к `Document` (без `Session::execute`). Сервер — relay с
журналом и порядком: он не исполняет команды, только фиксирует последовательность и
раздаёт.

- **Пиксельные дельты:** `PaintTiles` несёт только реально изменённые тайлы. Одна и та же
  координата у двух акторов: OT-правило «оба применяются в порядке сервера, поверхность =
  объединение непересекающихся пикселей» требует пиксельного сравнения внутри тайла —
  тайл 256² = 65 536 px, и в дельте нужен маскированный слой (какие пиксели писал автор),
  а не только «новые байты». В upstream кисть пишет анти-алиасящие дэбы, поэтому «маска
  штриха» есть, но её надо экспортировать из `paint` (сейчас её нет).
- **Per-user undo:** у каждого актора свой стек обратных операций; undo = инверсия,
  трансформированная против операций, пришедших после неё. Инверсия для `SetLayerProps`
  тривиальна, для `PaintTiles` — «предыдущие байты тайла» (они есть в локальном снапшоте),
  для `InsertLayer` — `DeleteLayer`, для `SetTextRuns` — предыдущие раны. Глобальные
  снапшоты сервера здесь для undo не нужны.
- **Структура:** `Reorder` трансформируется по якорю (`anchor` — стабильный `LayerId`),
  вставки в одну точку упорядочиваются сервером; удаление слоя, который правит другой,
  требует правила «delete wins + правки переезжают в копию» или блокировки.
- **PSD round-trip:** полностью зависит от того, насколько точно клиент воспроизводит
  `Session`-путь. Любая операция, минующая команду, обходит и `io`-маппинг
  (`psd_blocks`, `psd_id`, `psd_raw`), поэтому commit обязан идти через `Headless::save`.
- **100+ МП:** каждый клиент держит полный документ и исполняет чужие пиксельные операции
  сам — 400 MB на слой плюс история. В браузере (лимит 1.5 GiB, `prefs.rs:733`) это
  невозможно; на desktop — возможно, но каждая чужая кисть тратит CPU каждого клиента.
- **Где ломается в этом формате:** OT-правила надо писать для 33 полей `Document`,
  7 вариантов `LayerContent`, 17 `Adjustment`, 10 эффектов — и всё это без единой
  существующей инверсии в коде. Это второй, параллельный `Session`, который обязан
  повторять семантику `edit_with` (смарт-кэши, `fix_selection`, damage, `psd_raw`).

## 2. Вариант B — авторитетный сервер + журнал команд (сервер исполняет)

Клиент шлёт **нормализованную команду** `{opId, sessionId, actor, baseVersion, cmd,
params, context}`, где `params` уже развёрнуты (явный `layer: LayerId`, `target: pixels|
mask|filterMask`, точки штриха с `seed`, `coalesce`). Сервер:

1. проверяет роль/ACL и `baseVersion`;
2. исполняет команду в своей `Session` (headless, `photocraft-engine` c `cpu-only`);
3. берёт дельту из «до/после» через `each_changed_tile`/сравнение полей `Layer`:
   тайлы (coord+zstd), параметры слоя, вставки/удаления, кэши-инвалидации;
4. рассылает `{opId, version, command, delta}`; пишет журнал сессии + периодический
   снапшот `.pcraft` (не клиентской историей).

- **Пиксельные дельты:** сервер уже имеет `before`/`after` из `edit_with`, а
  `each_changed_tile` даёт ровно изменённые тайлы (merge-walk по `BTreeMap`, сравнение
  `Arc`-указателей): кисть на 30 px меняет 1–4 тайла = 1–4 × 256 KiB до сжатия. Клиент
  применяет замену `Arc`-тайла — GPU перегружает только эту страницу
  (`crates/gpu/src/lib.rs:5-12`), CPU перекомпоновывает damage-rect. Та же операция
  штриха не рассылается как «намерение» — только результат, поэтому детерминизм
  `paint.stroke` между платформами не требуется.
- **Per-user undo при глобальных снапшотах:** снапшоты `ops` остаются локальной историей
  клиента и на сервере не используются для undo. Сервер ведёт журнал **с автором** и
  инверсией на операцию (инверсия строится из дельты: предыдущие байты тайлов, прежние
  значения полей, обратный `layer.moveTo`, `layer.delete` ↔ восстановление из дельты).
  `undo` = новая операция `inverse(op)` с новым `version`; конфликт цели (слоя уже нет) —
  no-op + уведомление, а не откат чужих правок. Это закрывает TASK §6 без переписывания
  `ops`.
- **Структурные конфликты:** сервер сериализует команды; `layer.delete` в очереди после
  чужого `paint.stroke` означает, что штрих уже применён к удаляемому слою — сервер может
  либо отказать в delete с `409`/«слой правится», либо применить delete и сохранить
  правки в «удалённой копии» (отдельный слой/корзина) — решение уровня протокола, а не
  OT. `layer.moveTo` с id-якорем не сдвигается от вставок.
- **PSD round-trip:** commit — один писатель, `Headless::save` тем же кодом, что одиночный
  режим (`io/src/psd_export.rs`); 308/309 round-trip (`docs/file-format-parity.md:26`)
  остаётся точкой отсчёта. Риск только один: регенерация adjustment/type-блока после
  мержа (`psd_export.rs:495-520`) — проверяется тестом «два клиента → commit → round-trip».
- **100+ МП:** документ живёт на сервере: 100 МП RGBA8 = 400 MB на слой, RAM-бюджет тайлов
  2 GiB native (`raster/src/scratch.rs:23`), GPU не обязателен (`cpu-only`). Клиенту едут
  тайлы, а не документ. Браузерный клиент ограничивается лимитом документа (например,
  ≤ 24–36 МП) — это политика, а не протокол.
- **Где ломается в этом формате:** сервер обязан уметь всё, что умеет `Session`, включая
  фильтры и смарт-объекты (тяжёлый CPU: P21 Content-Aware Fill 10 МП = 1.5 s бюджет,
  `perf/budgets.toml:316-321`), и держать документ в памяти; для 100+ МП это дорого, а
  GPU-композит на сервере — отдельная инфраструктура.

## 3. Вариант C — CRDT на подмножестве модели

Дерево слоёв — sequence-CRDT (позиционные id вместо `Vec`-индексов), свойства слоя —
LWW-регистры по полям, тайлы — LWW-регистры `(layer, part, tile) → bytes` с
детерминированным разрешением, текст/вектор — параметры как LWW, производные кэши — вне
CRDT. Сервер — relay + персистентность + снапшоты; сходимость конструктивная, offline
естественный.

- **Пиксельные дельты:** LWW на тайл = потеря правок второго актора в том же тайле, а
  TASK §5 требует «потерь быть не должно (пересечение только по реально изменённым
  пикселям)». Чтобы выполнить, нужен per-pixel stamp (65 536 штампов на тайл) или
  «слой-на-актора» с последующим merge — и то и другое меняет модель рендера.
- **Per-user undo:** в CRDT нет глобальной последовательности; undo «своих» операций —
  отдельная семантика (инверсия + проверка, что значение всё ещё моё), классический
  Yjs-подход требует параллельной истории. При этом undo не должен воскрешать удалённое
  другим — правила те же, что в B, но без серверного порядка.
- **Структура:** sequence-CRDT как раз силён: вставки не конфликтуют, удаление —
  tombstone. Но `Document.layers: Vec<Layer>` (`doc/src/lib.rs:956`, `LayerTree` над
  `Vec`) и `LayerTree` с ленивым индексом придётся заменить на структуру с позиционными
  id; это переписывание L1-крейта и всех 1 018 команд, читающих `doc.layers`.
- **PSD round-trip:** материализация в `Document` + `Headless::save` технически возможна,
  но «какой из кэшей (`text/shape/smart/fill cache`) выиграл» — LWW по расту, который
  зависит от шрифтов машины; при разных шрифтах commit даст другой рендер, чем видел
  автор.
- **100+ МП:** метаданные CRDT на тайл (1 600/слой × 30 слоёв = 48 000 регистров) плюс
  tombstone'ы; памяти на порядок больше, чем `BTreeMap<Arc>`; без compaction'а upstream
  (его нет) сессия растёт неограниченно.
- **Где ломается в этом формате:** три вещи сразу — пиксели (нужен per-pixel, а не
  per-tile), производные кэши внутри документа, и `Vec<Layer>` как основа всей командной
  поверхности. Плюс критерий 6 AGENDA — «не тащить тяжёлый CRDT-стек» — а готового
  CRDT для «изображение + 23 поля слоя + 7 видов контента» нет.

## 6. Рекомендация: **B** — авторитетный сервер + журнал команд, дельта = тайлы + параметры

PhotoCraft — command-first система с единственной точкой мутации и уже готовым
headless-хостом; B использует это напрямую, а не строит второй движок.

1. **Единица операции уже есть.** `Session::execute` (`execute.rs:14`), 1 018 команд,
   у каждой — машиночитаемая строка параметров (`param_schema.rs:1-16`) и проверка ключей
   (`param_check.rs:1-10`). Намерение нормализуется (явный `layer: LayerId`, `target`,
   точки + `seed`) и уходит как есть; клиенту не нужно понимать 33 поля `Document`.
2. **Дельта дешева и уже вычислима.** `edit_with` даёт `before`/`after`
   (`session/execute.rs:235-330`), `each_changed_tile` — изменённые тайлы
   (`damage.rs:12-40`), GPU перегружает только сменивший `Arc` тайл
   (`gpu/src/lib.rs:5-12`). Операция кисти = единицы-десятки тайлов, не мегабайты.
3. **Commit одним писателем.** `Headless::save` (`headless.rs:369-450`) уже умеет
   `.pcraft`/PSD/PSB/ORA и использует тот же `io`-маппинг, что одиночный режим; `.pcraft`
   content-addressed (`format/src/lib.rs:1-20`) — хэш коммита сравним. Round-trip 308/309
   (`docs/file-format-parity.md:26`) остаётся базой.
4. **Per-user undo не требует переписывать `ops`.** Снапшоты остаются клиентской
   историей; серверный журнал хранит автора и инверсию, undo = новая операция. Это
   единственный вариант, где глобальные снапшоты не мешают требованию TASK §6.
5. **Структура не требует OT.** `insert_above(Option<LayerId>)` (`doc/lib.rs:1335`) и
   `layer.moveTo{target, position}` уже id-якорные; сервер сериализует, порядок
   детерминирован. OT по 33 полям `Document` (вариант A) — это второй движок, который
   обязан повторить `edit_with`, кэши, `fix_selection`, damage и `psd_blocks`.
6. **100+ МП.** Сервер — native с `cpu-only` и RAM-бюджетом 2 GiB (`raster/src/scratch.rs:23`);
   браузер остаётся клиентом с лимитом документа (wasm: 1.5 GiB памяти
   `prefs.rs:733`, нет потоков, нет WS — `apps/photocraft-web/src/main.rs:1-16`).

**Обязательные уточнения, иначе B развалится на фото:**

- **Нормализация конверта обязательна.** `paint.stroke` по умолчанию берёт активный слой,
  цвет и кисть из сессии; в конверт едут `layer: LayerId`, `target`, полный набор
  `points` с pressure/time, `seed`, `brush`. Иначе «одинаковая» команда даст другой штрих.
- **Пиксельная дельта — отдельный тип кадра**, не «команда целиком»: `Tiles{layer, part,
  coord, zstd, from_version}` + параметры слоя. Команда `paint.stroke` остаётся в журнале
  для аудита/undo, но не рассылается как единственный payload (иначе каждая реплика
  растеризует штрих сама, а `paint.stroke` помечен `incomplete` в
  `crates/engine-paint/src/install.rs:32-54` — его схема ещё не полная).
- **Производные кэши не мержатся.** `TextLayer::cache`, `ShapeLayer::cache`,
  `SmartObject::cache`, `FillCache` — вне дельты; после правки параметров клиент
  пересчитывает сам, commit — на сервере. LWW на кэш (вариант C) даст растр с чужими
  шрифтами.
- **Структурные команды — эксклюзивная секция.** Пока сервер исполняет `layer.delete`/
  `layer.moveTo`/`layer.smartObjects.replaceContents`, пиксельные дельты в очередь; клиенты
  не применяют структурную команду оптимистично, а ждут подтверждённой дельты.
- **Снапшот — `.pcraft`, не история.** Сервер каждые N операций/минут пишет `.pcraft`
  (content-addressed, инкрементально, `format/src/store.rs`), журнал компактится по
  версии снапшота. Клиентская история `ops` (50 состояний) не уезжает на сервер.

**Что берём из A:** нормализованный конверт намерения (явные значения вместо «активного
слоя»), `opId`/`baseVersion`, отдельный тип «структурная операция». **Что берём из C:**
ничего для документа; только принцип «presence эфемерен, без журнала» и «свойства —
LWW там, где сервер не нужен» (например, имя слоя при одновременном переименовании).

## 7. Риски и как их снимаем

| Риск | Митигация |
|---|---|
| Сервер не тянет 100+ МП (память 400 MB/слой, CPU-фильтры) | RAM-бюджет 2 GiB + спилл на диск (`raster/src/scratch.rs:23`), лимит документа и числа участников, `cpu-only` без GPU; мерить `Document::clone`/compose на хосте `agents` до фиксации лимитов |
| Пиксели в одном тайле теряются при замене | дельта несёт маску реально изменённых пикселей (из `paint`), сервер применяет поверх текущего тайла и рассылает результат; тест «две кисти в одном тайле» |
| `layer.delete` против правок другого | сервер: `409`/«перемещено в корзину» + операция восстановления; тест delete-vs-paint |
| PSD degradation после мержа | commit только через `Headless::save`; тест round-trip 308/309 на слитом документе; сравнение рендера и структуры слоёв |
| Undo воскрешает чужое | инверсия применяется как новая операция с проверкой цели; no-op + уведомление, если цель исчезла |
| Клиент «залип» на версии | `baseVersion` + `resync` полной `.pcraft`-снапшот-парой; `409` в кабинет → «Сохранить копию» (TASK §7) |
| Браузер: нет WS/потоков/памяти | transport-крейт на `web-sys` WebSocket + backpressure; лимит документа и отказ выше него; presence ≤ 10 Гц |
| Не проверено | время compose/GPU для 100 МП, размер типичного `.pcraft`, `Document::clone` на 50 состояниях, детерминизм `paint.stroke` между платформами — измерить на `agents` до Phase 1 |

## 8. Позиция PhotoCraft по десяти измерениям

| # | Измерение | Позиция |
|---|---|---|
| 1 | Единица операции | нормализованная команда `(id, params, context)` + серверная дельта тайлов/полей |
| 2 | Идентификаторы | `LayerId` + актор-диапазон (или выдача сервером); части — `(layer, target)`; новые id — только после подтверждения |
| 3 | Порядок и версии | серверный счётчик `version`, `baseVersion`, идемпотентность по `opId`; Lamport не нужен |
| 4 | Конфликты | серверный порядок + пиксельный merge в тайле; структурные — эксклюзивно |
| 5 | Снапшоты | `.pcraft` (content-addressed) каждые N операций + compaction журнала; клиентские `ops`-снапшоты не на сервере |
| 6 | Presence | отдельный эфемерный канал: курсор, выделение/маска, активный слой, вьюпорт; ≤ 10 Гц, без журнала |
| 7 | Топология сервера | один sync-сервис, app-воркер = `Headless`/`Session` на сессию документа |
| 8 | Auth и lease | JWT из кабинета (file/session/role), сервер проверяет viewer; lease одна сессия на документ |
| 9 | Commit | сервер собирает `.pcraft`/PSD через `Headless::save`, отдаёт байты кабинету; `409` при смене файла вне сессии |
| 10 | Offline и undo | per-user undo по журналу инверсий; offline — очередь команд с проверкой `baseVersion`, без автономной сходимости |
