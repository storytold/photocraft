# JPEG 2000

PhotoCraft's first JPEG 2000 implementation uses the standalone, pure-Rust
`oxideav-jpeg2000` 0.0.17 API, with its registry/default features disabled.
The dependency temporarily pins the exact fork commit
`c61387382c2335143c7717ea578724fbe37e9b2b` for the decoder and encoder optimizations in
[upstream PR #17](https://github.com/OxideAV/oxideav-jpeg2000/pull/17) and
[upstream PR #20](https://github.com/OxideAV/oxideav-jpeg2000/pull/20).
Replace this pin with an upstream release containing both fixes when available.
The default build reads and writes JP2 and bare J2K/J2C codestreams. No native
OpenJPEG library is introduced, and the workspace's Rust 1.95 minimum stays unchanged.

## Supported subset

- Unsigned, full-resolution Gray, Gray + alpha, RGB and RGB + alpha components,
  with a common precision of 1–16 bits. Input precisions up to 8 bits scale to
  the full U8 range; 9–16 bits scale to the full U16 range.
- Reversible 5/3 and irreversible 9/7 decoding; lossless 8-/16-bit encoding by
  default. RGB colour transforms preserve the separate alpha component.
- JP2 ICC profiles and capture resolution. A raw codestream has neither field;
  document exports convert RGB to sRGB before dropping its profile and report
  the omitted resolution/profile information.
- JP2-compatible JPX containers with one codestream use the same subset.
  General JPX, palettes/channel mappings, signed or subsampled components,
  mixed component precisions and YCbCr/CMYK layouts are unsupported.
  One colour specification is accepted; recognized ICC device models must be
  Gray or RGB and agree with the component count. Channel definitions must
  describe Gray/RGB and optional whole-image straight alpha. Without channel
  definitions, two and four components use the conventional trailing-alpha
  interpretation. Premultiplied alpha is unsupported.
- EXIF, XMP and other container metadata are not retained in this first slice.
  Container XML/UUID metadata triggers an import warning; exports report losses
  through the existing fidelity-warning API.

The header preflight has further coding-tool restrictions, documented in
`crates/codecs/src/codecs/jpeg2000/preflight.rs`. Unsupported tools return an
explicit error instead of producing pixels under an unsupported interpretation.

Reversible QCD/QCC tables are limited to 22 magnitude bits
(`guard bits + exponent - 1`), including main-header and tile overrides.
Together with the limit of 32 wavelet levels, this keeps the backend's 5/3,
reversible colour transform and DC-shift intermediates within `i32`.
Normal 8-/16-bit encoder output fits this bound. Otherwise valid streams with
larger guard/exponent headroom, including unused overridden tables, are
unsupported in this first subset. Irreversible 9/7 quantization is unchanged.

## Export controls

`EncodeOptions::jpeg2000_codestream` selects raw codestream output in the codec
API. Document export chooses the representation from the requested suffix:
`.jp2` produces JP2, `.j2k` and `.j2c` produce raw codestreams.

`jpeg2000_quality: None` is lossless. An explicit quality from 1 to 100 requests
9/7 lossy compression with a codestream byte budget of
`512 + floor(native sample bytes * (quality / 100)^2)`. CLI `--quality 80`
therefore budgets 64% of the converted uncompressed sample bytes, plus 512
bytes for headers. JP2 container metadata is additional; structural minimums
can exceed very small targets. Rate allocation avoids repeatedly decoding
full-size candidates during a PSNR search. This is a PhotoCraft policy, not
JPEG/libjpeg's quality scale, a PSNR guarantee or an exact compression ratio.
Even quality 100 uses lossy 9/7; omit quality for lossless output. Export As
initially offers lossless JP2 without a quality slider.

## Limits and validation

Container boxes and the codestream headers are checked before allocating
samples. `Limits` constrain dimensions, pixels, decoded buffers, header metadata
and a conservative estimate of component, packet and code-block working memory.
The backend receives its own dimension, pixel and component-plane budgets too.
This is a decompression/workload guard, not a total process RSS limit.
The current estimate includes 48 bytes per component sample, eight times the
compressed codestream size, and header/packet/code-block bookkeeping. The
backend retains coefficient state, global integer planes and floating-point
wavelet/conversion arrays together, reaching about 34 bytes per sample before
additional records. A separate allowance of `32 × (largest tile axis + 16)`
bytes per component covers row/column scratch, which can dominate skinny tiles.
Container metadata and codestream work share the same allocation budget.
This deliberately conservative accounting differs from a final-pixel-only
budget: the sample allowance alone for 24 MP RGB is 3.22 GiB, and for RGBA
4.29 GiB, before compressed data and other overhead. Both exceed the WebAssembly
default of 2 GiB; native builds default to 8 GiB. Large web imports therefore
report a limit error. Raising a budget does not establish that the host can
allocate it.

OpenJPEG is the authoritative pixel reference for standalone validation;
the performance patch uses it as a black-box oracle and copies no reference code.
Tests also use generated images and an independent `hayro-jpeg2000` 0.4.1 decoder
(default features disabled), including original 16-bit samples, alpha, tiny and
odd dimensions, raw/container output, metadata, precision scaling and malformed
headers. No PdfCraft adapter code or fixtures are copied. PdfCraft informed the
integration approach; its older 8-bit PDF adapter cannot establish high-depth
image fidelity or JPEG 2000 encoding support.

Sources: [standalone backend release](https://github.com/OxideAV/oxideav-jpeg2000/tree/v0.0.17),
[independent decoder](https://github.com/LaurenzV/hayro/tree/main/hayro-jpeg2000),
[requested feature scope](https://github.com/storytold/photocraft/issues/1047).

## Performance

Run the standalone 24 MP benchmark on a native 64-bit target:

```sh
cargo run --release -p photocraft-codecs --example jpeg2000_perf
```

It generates deterministic 6000×4000 RGB gradients with modest noise in U8 and
U16, times lossless JP2 encoding and decoding separately, and verifies every
native sample byte. Image generation and verification are outside the reported
codec timings. Each depth runs in turn; no image files are written.

Add `-- --lossy` to also measure quality-80 RGB8 encoding/decoding and report
PSNR, checked against a 35 dB floor. The example prints encoded byte counts and
single-run elapsed times. Record the CPU, Rust version and command alongside
results when comparing revisions.
The pinned backend fix hoists a repeated block-wide decoded-bit count scan out
of the coefficient loops. In standalone same-stream 6000×4000 RGB measurements
on an Intel Core Ultra 7 265T / Debian 13 (Rust 1.98.1, opt-level 3, LTO off,
16 codegen units), the median of
three decodes improves from 42.710 s to 9.333 s for RGB8 and from 53.489 s to
20.061 s for RGB16. Every native sample remains exact, with OpenJPEG separately
confirming all component values. Generation, file reading and verification are
outside the Rust decoder timings. These results describe these generated
streams on that host; they do not establish a universal speedup. Smaller
512×384 Gray/GrayA/RGB/RGBA streams at both depths improve by 2.63–4.75×.

The second backend fix skips neighbour reads during MQ magnitude refinement
once the coefficient's fixed refinement context is already known. Paired
three-round lossless encoding measurements on the same 24 MP host and inputs
reduce RGB16 `encode()` time from 19.470 s to 17.553 s, or 9.85%. RGB8 changes
from 8.691 s to 8.632 s (0.68%), within observed noise; no RGB8 gain is established.
All twelve complete before/after JP2 outputs are byte-identical and preserve
the OpenJPEG-verified native samples. This reduces constant work, with no
change to compression settings, file sizes or coding decisions.

A separate controlled single-thread OpenJPEG 2.5.3 comparison on these inputs
uses reversible 5/3, four resolutions, 64×64 code blocks, LRCP, RGB MCT and one
lossless layer in one full-image tile. Including packed-to-planar conversion
and excluding disk I/O, the original Rust encoder takes 8.682 s / 19.490 s
(RGB8/RGB16) versus OpenJPEG's 3.716 s / 9.691 s, as three-run medians.
Same-raw-input process wall times, including reading and writing, are
8.706 s / 19.550 s versus 3.744 s / 9.753 s. The Rust fix reduces work but
does not close this remaining encoder gap. OpenJPEG's POSIX CLI prints CPU
time; elapsed comparisons use a monotonic timer rather than that CLI value.

The pinned backend also offers a quick standalone encoder benchmark:

```sh
cargo run --release --no-default-features --example encoder_perf -- 512 512
```

Run it in the backend checkout. It reports three native-depth RGB8/RGB16
encode times and their median, with generation and exact roundtrip validation
outside the timing. Use `6000 4000` for the 24 MP case.
